# PDIS MCP implementation plan

> **For agentic workers:** Use superpowers:executing-plans task by task.

**Goal:** One opt-in, authenticated, client-neutral MCP server exposing Searcher.

**Architecture:** HTTP routes and MCP tools call application operations in
`api/operations/`. Services remain transport-free and stateless. MCP owns its
protocol/authentication boundary, not provider construction or search meaning.

**Tech stack:** Python 3.11, FastAPI, official MCP Python SDK, Pydantic, OAuth JWT
verification against a configured issuer/JWKS/audience. No authorization server
or employee identity store is added.

**Spec:** The approved design in this conversation: Searcher first, shared web/MCP
operations, standard remote access, disabled until configured, deployment handoff
separate from code completion. Document tools are future registrations, not part
of this first release.

## Constraints and ownership

- Preserve existing HTTP endpoints, form parameters, NDJSON events and results.
- `api/operations/searcher.py`: typed input, source validation, runtime preparation,
  source discovery and result assembly; call service package exports only.
- `api/execution.py`: one process-wide run capacity shared by HTTP and MCP.
- `api/mcp/settings.py` and `auth.py`: fail-closed configuration and JWT verification.
- `api/mcp/server.py`: SDK construction and mounting; `tools/searcher.py`: registrations.
- API owns credentials. No provider/model parameters in MCP inputs.
- Mount under `/api/mcp`; discovery must be reachable through existing `/api` ingress.
- Explicitly enabled remote transport always requires OAuth configuration. Never
  provide an unauthenticated production fallback.
- Untrusted result excerpts remain data; never instructions. Source failures retain
  their lanes. Operation errors have machine-readable codes, not invented findings.
- One worker, no hidden run/result sessions, no background deployment changes.
